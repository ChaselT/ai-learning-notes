# 03-RAG检索增强 MOC

> 本阶段目标：从"会调 LLM API"变成"能把私有数据接进 LLM 并且说得清效果好坏"。
> RAG 是 AI 应用岗**面试必考、落地最广**的形态——阶段 1 你让模型会说话，这一阶段让它说得有依据。
> 所有代码写到 `E:\workspace\AiStudy\phase2-rag\` 下。
>
> **本地硬件基线与显存预算（2026-08-16 按阶段 1 实测数据重算）**
>
> 阶段 1 你只跑一个模型，17GB 随便造；**阶段 2 要同时驻留三个模型**，账完全不一样：
>
> | 项 | 显存 | 出处 |
> |---|---|---|
> | 可用上限 | **19.78 GB** | ex10 实测（22 标称 − 桌面常驻 2.2） |
> | bge-m3 embedding | 1.2 GB | Ollama library |
> | bge-reranker-v2-m3 (q8) | 0.64 GB | 第 8 课用；q4_k_m 版仅 438MB |
> | **剩给生成模型 + KV cache** | **≈ 17.9 GB** | |
>
> 于是：
> - `qwen3.5:27b`（权重 ~16GB）→ 只剩 1.9GB 给 KV cache，按 ex10 测的 **64 MB/1K** 算，
>   `num_ctx` 上限约 **30K**。跑得起来但很紧——而 RAG 恰恰要塞多个 chunk，吃上下文
> - **建议主力换成中档模型**（如 `qwen3.5:9b`，约 6GB），留 12GB 给 KV cache，
>   `num_ctx` 可以开到很宽裕；27b 留作效果对照
> - 拉完先用 `phase1-llm-api/chat_service/probe_ollama_parallel.py` 测是否单槽：
>   **视觉模型在 llama.cpp 里走单槽路径，`OLLAMA_NUM_PARALLEL` 对它无效**（[[错题与复盘#E51]]）。
>   建库要批量 embed，能并发差别很大
>
> ⚠️ **不要为了追新换 `qwen3.8:27b`**：它权重 18GB，比 3.5 大 1-2GB，
> 在上面这本账里等于直接吃掉 KV cache 的余量，收益不明而代价明确。
>
> **版本基线：本文按 2026-08-07 联网核对**。RAG 生态半年一变，笔记里凡是写了具体模型名/版本号的地方，
> 到阶段 2 后期请重新核一遍（这就是 [[AI学习地图]] 里说的知识库 lint）。

## 为什么第 11 课标了两颗星

你在 [[实战资产-video-clipper-pro]] 里最大的短板就是**零 eval 体系**（LLM 自评分、无 ground truth）。
阶段 1 的 ex09 你已经写过一个最小原型（`compare_chart_data` 把结构错误与数值错误分开报），
这一课是把它扩成完整方法论。

面试里"你怎么知道你的 RAG 做得好"这个问题，答不上来基本就废了——**会评估是区分调包侠和工程师的分水岭**。

## Java 类比速查

| RAG 概念 | Java 世界的对应物 |
|---|---|
| Embedding | 把对象算成 hashCode，但相似对象的 hash 也相近 |
| 向量数据库 | 一个只会按"相似度"查询的 NoSQL |
| HNSW 索引 | 跳表（SkipList）的高维版本，牺牲精确换速度 |
| BM25 | Lucene / Elasticsearch 的老本行，全文检索 |
| 混合检索 | 两个数据源查完做 merge，类似多路归并 |
| Rerank | 粗排 + 精排两阶段，跟推荐系统一个套路 |
| chunk | 分库分表里的"分片"，但切错了会丢语义 |
| Ragas | JUnit + 覆盖率报告，只是断言变成了模型打分 |

## 项目②：个人知识库问答系统

学完 1-11 课后开始，代码放 `E:\workspace\AiStudy\phase2-rag\project_kb_qa\`。

**功能要求：**

1. **文档入库**：支持 PDF / Markdown / TXT 至少三种格式，能增量添加不用重建全库
2. **检索链路**：混合检索（BM25 + 向量）→ rerank → 生成，每一层的参数可配置
3. **引用溯源**：回答中标注每句话来自哪个文档的哪一段，用户能点开看原文
4. **拒答**：检索不到相关内容时明确说"知识库里没有"，不许编
5. **评估报告**：自建 30+ 条问答评测集，给出召回率、忠实度等指标，**并且有一组对照实验**
   （比如"开 rerank vs 不开"、"chunk 512 vs 1024"），用数据说明你的参数为什么这么选
6. **Web 界面**：FastAPI + 简单前端 或 Gradio，能上传文档、提问、看引用

**语料建议**：用你自己熟悉的——公司的 Java 项目文档、你写的技术博客、
或者 `AiStudy` 这个仓库本身的笔记（**你最懂它，最容易判断答案对不对**，做评测集时省一半力气）。

**加分项**：多模态（PDF 里的图表能被检索到）；查询改写；对话式追问（多轮指代消解）。

**⚠️ 不要做的事**：别一上来就套 LangChain 全家桶。**前 11 课全部裸写**，
把每一步的输入输出看清楚，最后再考虑要不要用框架。阶段 3 学 LangGraph 时你会庆幸自己先裸写过。

## 验收标准

- 能解释每个分块/检索参数**为什么这么选**，并且有对照实验数据支撑（不是"感觉这样好"）
- 能说清 RAG 链路里哪一环最可能是瓶颈，以及怎么定位
- 评估报告里有召回率和忠实度的具体数字
