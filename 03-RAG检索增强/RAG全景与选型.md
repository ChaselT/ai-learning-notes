# RAG全景与选型

## 这是什么/为什么重要

RAG（Retrieval-Augmented Generation，检索增强生成）就一句话：**先查资料，再让模型带着资料回答**。

你在阶段 1 已经见过它的雏形——[[Function Calling]] 那课里 `read_file` 工具把文件内容塞回 messages，模型就能回答文件里的问题。RAG 是把这件事做到规模化：文档有一万份时，怎么知道该塞哪一段。

Java 类比：**RAG ≈ 查数据库再渲染模板**。模型是模板引擎，检索是 DAO 层。区别是 DAO 用 `WHERE id = ?` 精确匹配，而检索用"语义相近"来匹配——这个区别带来的全部麻烦，就是这一阶段要学的东西。

## 核心内容

### 1. 为什么需要 RAG：模型不知道的三类东西

| 类型 | 例子 | 为什么模型不知道 |
|---|---|---|
| **私有数据** | 你公司的接口文档、内部 wiki | 训练数据里没有 |
| **新数据** | 上周发布的版本说明 | 训练截止日之后发生的 |
| **长尾数据** | 某个冷门库的用法 | 见过但记不准，容易编 |

这三类不解决，模型会**编得很像真的**——回顾 [[错题与复盘#E32]]（幻觉会转移到可信回答的细节里）和 [[错题与复盘#E33]]（模型连自己的训练截止日期都说不准）。

### 2. 三条路线怎么选：RAG / 微调 / 长上下文

这是面试高频题，也是真实项目第一个要做的决策。

| | RAG | 微调 | 长上下文直接塞 |
|---|---|---|---|
| **解决什么** | 模型不知道的**知识** | 模型不会的**行为/风格/格式** | 一次性的少量资料 |
| **数据更新** | 改库即生效，秒级 | 要重新训练 | 每次都得重传 |
| **成本** | 检索开销 + 略增 token | 一次性训练成本高 | **token 成本线性暴涨** |
| **可溯源** | ✅ 能指出答案出自哪 | ❌ 说不清 | ⚠️ 勉强 |
| **典型场景** | 企业知识库、客服问答 | 固定输出格式、领域语气 | 单篇论文问答 |

**一句话决策**：
- 问题是"**它不知道**" → RAG
- 问题是"**它不会这么说/这么做**" → 微调（阶段 4 学）
- 资料就一两篇、用完即弃 → 直接塞进 prompt

真实项目里 **RAG + 微调经常一起用**：微调教格式和语气，RAG 供事实。

### 3. 长上下文没有干掉 RAG，原因有四个

2026 年主流模型上下文轻松到 256K（你本地的 `qwen3.5:27b` 训练上下文就是 262144，见阶段 1 ex10 实测），
于是总有人问："全塞进去不就行了？"

不行，四个原因：

1. **成本**：token 是线性计费的。10 万字资料每次问都重传一遍，问 100 次就是 100 倍。RAG 只塞相关的那几段
2. **显存**：你在 ex10 亲手测过——`num_ctx` 每涨 1K 吃 **64 MB** 显存；实测 27b 开到 **65536 仍全在 GPU（20GB）**，**81920 就开始往 CPU 卸载**。而卡的**可用**显存是 **19.78GB**（22 标称减去桌面常驻 2.2），不是 22。也就是说本地部署连 128K 都摸不到，更别说把十万字资料常驻在上下文里
3. **注意力稀释**（lost in the middle）：上下文越长，模型对中间部分的注意力越差。塞 10 万字的效果**未必好过**精准塞 2000 字
4. **不可溯源**：全塞进去，你没法知道答案是根据哪一句得出的——而 [[引用溯源与幻觉抑制]] 是企业落地的硬requirement

> [!tip] 反过来说
> 长上下文让 RAG **变简单了**：以前要精挑细选 3 个 chunk，现在可以放心送 10 个，
> 召回压力小了很多。它是 RAG 的助力，不是替代品。

### 4. RAG 的完整链路

```text
【离线·建库】
  文档 → 解析 → 分块 → 向量化 → 存入向量库
   ①      ②      ③       ④          ⑤

【在线·问答】
  问题 → 查询改写 → 检索(向量+BM25) → 重排 → 拼 prompt → 生成 → 带引用的回答
   ⑥       ⑦            ⑧             ⑨       ⑩        ⑪        ⑫
```

对应本阶段的课程：

- ②[[文档加载与解析]] ③[[分块策略]] ④[[Embedding原理与相似度]] ⑤[[向量数据库与索引原理]]
- ⑦[[查询改写与多查询]] ⑧[[混合检索]] ⑨[[重排Rerank]] ⑫[[引用溯源与幻觉抑制]]

**记住这张图**。后面每学一课，回来标记你在哪一环——RAG 出问题时，第一件事就是定位是哪一环烂了。

### 5. 效果不好时，问题多半不在你以为的地方

新手直觉：换个更强的生成模型。**通常没用。**

按经验，RAG 效果差的原因分布大致是：

| 环节 | 占比 | 典型症状 |
|---|---|---|
| **解析与分块**（②③） | ~40% | 表格被拆碎、代码块断成两半、标题和内容分家 |
| **检索与重排**（⑧⑨） | ~40% | 该找的没找到（召回问题）；找到了但排在第 20 位 |
| 生成（⑪） | ~20% | 资料给对了但答歪了、编了资料里没有的东西 |

**"垃圾进垃圾出"在 RAG 里是字面意义的**——PDF 解析把表格拍扁成一行乱码，后面做什么都救不回来。

所以本阶段的时间分配也该是这样：别急着调 prompt，先把前半段做扎实。

### 6. 一个最小可跑的 RAG（30 行）

先建立整体感，细节后面慢慢拆。这段代码**先读懂，别急着背**：

```python
"""最小 RAG：无向量库、无分块策略，只为看清骨架。"""
import numpy as np
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

# ① 假装这是切好的知识库
CHUNKS = [
    "公司的报销流程：先在OA提交申请，主管审批后转财务，财务3个工作日内打款。",
    "年假规则：入职满1年5天，满3年10天，满5年15天，当年未休完可顺延至次年3月。",
    "考勤制度：弹性上班9:00-10:00，每日工作8小时，月度迟到超过3次扣绩效。",
]

def embed(texts: list[str]) -> np.ndarray:
    """② 把文本变成向量（第 2、3 课细讲）"""
    resp = client.embeddings.create(model="bge-m3", input=texts)
    return np.array([d.embedding for d in resp.data])

def retrieve(question: str, k: int = 2) -> list[str]:
    """③ 检索：算余弦相似度，取最像的 k 个"""
    doc_vecs = embed(CHUNKS)
    q_vec = embed([question])[0]
    # 归一化后点积 = 余弦相似度
    sims = doc_vecs @ q_vec / (
        np.linalg.norm(doc_vecs, axis=1) * np.linalg.norm(q_vec)
    )
    return [CHUNKS[i] for i in np.argsort(sims)[::-1][:k]]

def ask(question: str) -> str:
    """④ 把检索结果拼进 prompt，让模型带着资料回答"""
    context = "\n".join(f"- {c}" for c in retrieve(question))
    resp = client.chat.completions.create(
        model="qwen3.5:27b",
        messages=[
            {"role": "system",
             "content": "只根据【参考资料】回答；资料里没有就说'知识库中未找到'，不许编。"},
            {"role": "user", "content": f"【参考资料】\n{context}\n\n【问题】{question}"},
        ],
        temperature=0,
    )
    return resp.choices[0].message.content

print(ask("年假能顺延吗？"))
```

这 30 行里已经有了 RAG 的全部要素：**向量化、相似度检索、上下文注入、拒答约束**。
后面 12 课做的事，本质上都是把这四步中的某一步做深。

> [!warning] 这段代码的问题（你现在就该看得出来）
> 1. 每次提问都重新 embed 全部文档——正式系统要预先建库
> 2. 没有分块，chunk 就是整句
> 3. 只有向量检索，问"报销要几天"这种带数字的会翻车（[[混合检索]] 会讲）
> 4. 没有 rerank，top-k 直接送给模型
> 5. 没有引用溯源，用户不知道答案从哪来
>
> **能自己数出这几条，说明你已经理解 RAG 的骨架了。**
