# Embedding原理与相似度

## 这是什么/为什么重要

Embedding 就是**把一段文本变成一串浮点数**，且这串数字有个关键性质：**意思相近的文本，数字也相近**。

Java 类比：`hashCode()` 也是把对象变成数字，但 hash 追求的是"不同对象尽量散开"——`"猫"` 和 `"猫咪"` 的 hashCode 毫无关系。Embedding 恰恰相反，它要让 `"猫"` 和 `"猫咪"` 落在很近的位置。

**这是整个 RAG 的地基**：没有它，"语义检索"无从谈起，你只能做关键词匹配。

## 核心内容

### 1. 向量长什么样

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")

resp = client.embeddings.create(model="bge-m3", input=["报销流程"])
vec = resp.data[0].embedding
print(len(vec))      # 1024  ← 维度
print(vec[:5])       # [-0.021, 0.043, 0.008, -0.017, 0.031]  ← 就是一串小数
```

几个必须建立的直觉：

- **维度是模型定死的**，不是你选的。`bge-m3` 是 1024 维，有的模型 768、1536、4096
- **同一个库里的向量必须来自同一个模型**——换模型等于换坐标系，老向量全部作废，得重建库
- **维度不是越高越好**：高维更能表达细微差别，但存储和计算成本线性上升，且容易过拟合到训练分布

> [!warning] 换 embedding 模型 = 重建整个向量库
> 这是 RAG 项目最贵的一次决策失误。选型要在建库**之前**做完（下一课专门讲），
> 库建到几百万条再想换，就是几天的重跑。

### 2. 相似度：三个公式，实际只用一个

假设两个向量 A、B：

| 度量 | 公式 | 含义 | 取值 |
|---|---|---|---|
| **余弦相似度** | `A·B / (‖A‖‖B‖)` | 只看**方向**，不看长度 | -1 ~ 1，越大越像 |
| 点积 | `A·B` | 方向 + 长度都算 | 无界 |
| 欧氏距离 | `‖A-B‖` | 空间中的直线距离 | ≥0，越小越像 |

**实践中 95% 的场景用余弦相似度**，原因：文本长度会影响向量的模长（长文本模长往往更大），
而我们关心的是"意思像不像"，不是"谁更长"。余弦把模长除掉了，只留方向。

关键技巧：**如果向量已经归一化（模长=1），余弦相似度就等于点积**。

```python
import numpy as np

def cosine(a: np.ndarray, b: np.ndarray) -> float:
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

def normalize(v: np.ndarray) -> np.ndarray:
    return v / np.linalg.norm(v)

a, b = np.array([1.0, 2.0, 3.0]), np.array([2.0, 4.0, 6.0])
print(cosine(a, b))                      # 1.0  ← 方向完全相同（b 是 a 的 2 倍）
print(normalize(a) @ normalize(b))       # 1.0  ← 归一化后点积 == 余弦
```

所以生产系统的惯例是：**入库前就归一化，查询时只做点积**。点积是纯矩阵乘法，
GPU 和向量库都优化到极致，比每次现算余弦快得多。大多数向量库的 "cosine" 距离
底层就是这么实现的。

### 3. 相似度分数怎么解读——别设死阈值

新手最爱问："相似度大于 0.8 才算相关，对吧？"

**不对，而且这是个危险的习惯。** 原因：

1. **不同模型的分数分布完全不同**。有的模型任意两句中文都在 0.6 以上（分布挤在高位），
   有的模型 0.4 就算很相关了
2. **同一模型下，不同语言、不同长度的分布也不同**
3. 绝对值没有物理意义，**只有相对排序有意义**

正确做法：
- **优先用 top-k**（取最像的 k 个），而不是阈值
- 确实需要阈值时（比如"检索不到就拒答"），**必须用你自己的数据实测标定**——
  跑 50 条真实查询，看相关的和不相关的分数分别落在哪，再画线
- 标定出来的阈值**换模型就得重标**

> [!tip] 这条和阶段 1 的教训是一回事
> [[错题与复盘#E36]]（参数没报错不等于生效）、[[错题与复盘#E49]]（仪器精度决定算法）——
> 都是"别拿别处抄来的数字当自己的基线"。相似度阈值是同一类陷阱。

### 4. 向量空间里藏着语义关系

经典演示（词向量时代的例子，句向量同理）：

```text
vec("国王") - vec("男人") + vec("女人") ≈ vec("女王")
```

这说明向量空间里的**方向**编码了语义关系。RAG 用不到这么花哨的运算，但理解它有助于建立直觉：
**相似度检索的本质是在高维空间里找最近邻**，而"近"意味着语义相关。

### 5. Embedding 模型 vs 生成模型：两种不同的东西

| | Embedding 模型 | 生成模型（LLM） |
|---|---|---|
| 输入 | 一段文本 | 一段文本 |
| 输出 | **一个定长向量** | 下一个 token 的概率分布 |
| 典型大小 | 0.1B ~ 8B | 7B ~ 数百B |
| 架构 | 多为 encoder-only（BERT 系） | decoder-only（GPT 系） |
| 是否有"生成" | 无 | 有 |

**它们是两个独立的模型，各调各的 API**（`client.embeddings.create` vs `client.chat.completions.create`）。
一个 RAG 系统里同时跑两个甚至三个模型（embedding + rerank + 生成）是常态。

Java 类比：embedding 模型像 `MessageDigest`（输入任意长度，输出定长摘要），
生成模型像 `StringBuilder`（一点点往外吐）。

### 6. 一个必须知道的坑：非对称检索

用户查询是"**年假怎么算**"（短、口语、疑问句），文档是"**员工年休假管理办法：入职满一年…**"
（长、书面、陈述句）。这两者形态差异很大——直接算相似度，效果会打折。

这叫 **非对称检索**（asymmetric retrieval）。好的 embedding 模型会针对性训练，
并且**要求你给查询和文档加不同的前缀**：

```python
# bge 系列的典型用法：查询要加指令前缀，文档不加
query_text = "为这个句子生成表示用于检索相关文章：年假怎么算"
doc_text   = "员工年休假管理办法：入职满一年可享受5天带薪年假……"
```

**具体前缀怎么写，一定要查你所用模型的官方文档**——写错或漏写，检索效果可能掉 10 个点，
而且不会报错（又一个 E36 场景：没报错不等于用对了）。

4. **标定实验**：设计 5 个相关对 + 5 个不相关对，把各自的相似度分数列出来，
   回答：**你的数据上，阈值该画在哪？相关对的最低分和不相关对的最高分有重叠吗？**
5. 试试加/不加检索前缀（第 6 节），对比同一组查询的相似度分数变化

**完成标准**：相似度矩阵能打印出来；`np.allclose` 断言通过；
注释里有你标定出的阈值和**重叠情况的说明**（有重叠说明单靠阈值分不开，这正是要学 rerank 的原因）。
