# 分块策略

> ⚠️ 本篇含 2026 年的新方法（late chunking、contextual retrieval），
> 按 **2026-08-07** 联网核对。

## 这是什么/为什么重要

把长文档切成一段段（chunk），每段单独向量化入库。

**为什么必须切**：
1. embedding 模型有输入上限（`bge-m3` 是 8192 token，多数模型只有 512）
2. 整篇文档算一个向量，语义被平均掉了——一篇讲十件事的文档，向量谁也不像
3. 检索要返回**精确的那一段**给模型，不是整本书

**为什么难**：切小了丢上下文（"满 1 年 5 天"——什么满 1 年？），
切大了噪声多、语义不聚焦。这个矛盾没有通解，只能针对语料测。

Java 类比：像分库分表选分片键——切错了每次查询都要跨片聚合，性能和正确性一起崩。

## 核心内容

### 1. 四种切法，从笨到聪明

**① 固定长度切分**（最笨，但有时够用）

按字符数或 token 数硬切，通常带 overlap（重叠）防止边界处语义断裂。

```python
def fixed_chunk(text: str, size: int = 500, overlap: int = 50) -> list[str]:
    chunks, start = [], 0
    while start < len(text):
        chunks.append(text[start : start + size])
        start += size - overlap        # 关键：回退 overlap
    return chunks
```

问题：完全无视语义边界，一句话可能被从中间劈开。

**② 递归字符切分**（工程默认选择）

按优先级尝试分隔符：先按 `\n\n`（段落）切，太长再按 `\n`，再按 `。`，最后才按字符硬切。
好处是**尽量在自然边界断开**。这是 LangChain 的 `RecursiveCharacterTextSplitter` 干的事，
但你要**自己实现一遍**才知道它在做什么。

**③ 结构感知切分**（推荐，效果/成本比最高）

利用上一课保留的结构信息：按 Markdown 标题、PDF 章节、代码的函数边界切。

> 2026 年的最佳实践建议：**先上结构感知切分 + 适度 overlap**，
> 只有当内容是没有清晰结构的长篇散文、**且你测出了检索质量缺口**时，才上语义分块。

**别一上来就用最花哨的方法**——这句话本身就是这一阶段的核心态度。

**④ 语义切分**（贵，按需上）

逐句算 embedding，相邻句子相似度**骤降处**就是话题切换点，在那里断开。
效果好但要对每句话做一次 embedding，建库成本显著上升。

### 2. chunk 大小怎么定

没有标准答案，但有**决策框架**：

| 语料类型 | 建议起点 | 理由 |
|---|---|---|
| FAQ / 短问答 | 200-300 token | 每条本身就是完整语义单元 |
| 技术文档 | 500-800 token | 一个小节的典型长度 |
| 法律/合同 | 800-1200 token | 条款之间引用多，需要更多上下文 |
| 长篇叙述 | 300-500 + 大 overlap | 语义连续，靠重叠兜住边界 |

**overlap 一般取 chunk 的 10%-20%。**

⚠️ 硬约束：**chunk 的 token 数不能超过 embedding 模型上限**，
否则[[Embedding模型选型与本地部署|静默截断]]——后半段内容凭空消失且不报错。

⚠️ 另一个约束：chunk 太大会挤爆生成模型的上下文。
召回 5 个 chunk × 每个 1000 token = 5000 token，再加对话历史……
回忆 ex10 实测：本地 27b 在 `num_ctx=32768` 已占 18GB。**分块大小是有显存成本的**。

### 3. 2026 年的两个新方法

这两个都在解决同一个问题：**孤立的 chunk 丢失了文档级上下文**。

比如一段话写着"该方案的成本约为原来的 1/3"——"该方案"是什么？
单独看这个 chunk 谁也不知道，向量化之后它几乎检索不到。

**① Contextual Retrieval（上下文增强）**

入库前，用 LLM 给每个 chunk **生成一句话的上下文说明**，拼在 chunk 前面再向量化：

```text
原始 chunk：  "该方案的成本约为原来的 1/3。"
增强后：      "【本段出自《2026技术选型报告》第3章，讨论向量库自建方案】
              该方案的成本约为原来的 1/3。"
```

代价：建库时每个 chunk 多一次 LLM 调用。**本地模型跑这个正合适**——
零 API 成本，慢一点无所谓（离线任务）。这也是你本地 22G 显卡的价值所在。

**简化版本（零成本）**：把上一课保留的 `heading_path` 直接拼在 chunk 开头。
效果不如 LLM 生成，但**不花一分钱、不多一次调用**，性价比极高，建议先做这个。

**② Late Chunking（延迟分块）**

先把**整个长文档**送进 embedding 模型（要求模型支持长上下文，如 `bge-m3` 的 8192），
拿到每个 token 的隐藏向量，**之后再按 chunk 边界做池化**。

这样每个 chunk 的向量都"见过"全文，天然带上下文——而传统做法是先切开、
各自独立编码，chunk 之间互相不知道对方存在。

据 2026 年的公开数据，**late chunking 与 BM25 + rerank 组合使用，可将 top-20 检索失败率降低最多约 67%**。

代价：实现复杂，要能拿到 token 级隐藏状态（Ollama 的 embedding 接口给不了，
得用 sentence-transformers 自己写池化）。

> [!tip] 学习顺序建议
> 先把**结构感知切分 + heading_path 前缀**做扎实，建立 baseline 和评测集；
> 等第 11 课有了评估能力，再回来试 contextual retrieval 和 late chunking，
> **用数据证明它们值不值得**。
>
> 顺序反了的话，你会陷入"上了一堆高级技术但说不清有没有用"——
> 这正是 [[实战资产-video-clipper-pro]] 现在的状态（零 eval 体系）。

### 4. 特殊内容的处理

| 内容 | 怎么办 |
|---|---|
| **表格** | 别按字数切！整张表作为一个 chunk；太大就按行切但**每块都带表头** |
| **代码块** | 按函数/类边界切，别从函数中间断开 |
| **列表** | 尽量整体保留，条目之间是并列关系 |
| **图片** | 第 12 课 [[多模态RAG]] 专门讲 |

表头那条尤其重要：一行"张三 | 8 | 通过"没有表头就是天书。

### 5. 怎么判断分块好不好

**别凭感觉。** 三个可操作的检查：

1. **人眼抽查**：随机抽 20 个 chunk 读一遍，**能不能独立看懂**？
   看不懂就说明缺上下文
2. **长度分布**：画个直方图。如果有大量极短 chunk（<50 token），
   说明切分逻辑有问题（可能在标题处切出了孤立的标题行）
3. **端到端评测**：第 11 课学完后，用同一套评测集跑不同 chunk 大小，
   **看召回率**——这才是最终判据

第 3 条才是真答案，前两条是快速排雷。
