# 大语言模型工作原理速览

## 这是什么/为什么重要

你不需要会推导 Transformer 的数学，就像写 Java 不需要会写 JIT 编译器。但你必须理解 LLM 的"运行时行为模型"：它是怎么产出文字的、为什么会一本正经地胡说、模型名字里的 14B/Instruct/Q4 各是什么意思。这些认知直接决定你写 prompt、选模型、排查线上问题的水平。

## 核心内容

### 1. 本质：next token prediction

LLM 只做一件事：**给定前文，预测下一个 token 的概率分布，采样一个，追加到前文，循环**。

```text
输入: "Java 是一门面向"
模型输出概率: {"对象": 0.92, "过程": 0.03, "切面": 0.01, ...}
采样 → "对象" → 新输入: "Java 是一门面向对象" → 继续预测下一个...
```

用伪代码表达（这就是所有推理框架的内核循环）：

```python
def generate(prompt: str, max_tokens: int) -> str:
    tokens = tokenize(prompt)
    for _ in range(max_tokens):
        probs = model.forward(tokens)      # 一次前向计算，得到词表上的概率分布
        next_token = sample(probs)         # 按 temperature/top_p 采样
        if next_token == EOS:              # 生成到"结束符"就停
            break
        tokens.append(next_token)
    return detokenize(tokens)
```

关键推论（Java 工程师类比）：

- LLM 是**无状态函数**：`f(全部前文) -> 下一个token`，没有内部记忆，"记忆"全靠调用方拼接历史（详见 [[Chat Completions API]]）
- 输出是**采样**出来的，天然带随机性，同一输入两次结果可能不同（详见 [[采样参数详解]]）
- 逐 token 生成，所以天然适合流式返回（详见 [[流式输出与SSE]]）

### 2. 为什么会幻觉（hallucination）

模型的训练目标是"生成**像**训练语料的文本"，不是"生成**真**的文本"。它没有数据库可查，知识以模糊的统计规律压缩在权重里。所以：

- 问它不知道的事，它不会返回 `null`，而是生成"看起来最合理"的续写——编一个像样的答案
- 越具体的长尾事实（某个小库的 API 签名、某人生日）越容易编
- 幻觉**无法根除**，只能工程化缓解：让它引用给定资料（RAG）、让它调用工具查询（[[Function Calling]]）、要求结构化输出便于校验（[[结构化输出]]）

一句话：**把 LLM 当"能说会道但爱面子的实习生"，重要结论必须给它资料或让它查工具。**

判断"这个问题模型容易编"的三个信号：

- 长尾、具体、可验证的事实（版本号、日期、API 签名、引用文献）
- 训练截止日期之后发生的事
- 你自己都查不到标准答案的问题（模型更查不到）

### 3. 训练三阶段概览

| 阶段 | 做什么 | 产物 |
|---|---|---|
| 预训练 (Pretraining) | 海量互联网文本上做 next token prediction | Base 模型：只会"续写"，不会"对话" |
| SFT (监督微调) | 人工标注的"指令→回答"对话样本上微调 | Instruct/Chat 模型：会听指令、按对话格式回答 |
| RLHF (人类反馈强化学习) | 人对多个回答排序，训练奖励模型再强化学习 | 对齐后的模型：回答更符合人类偏好、更安全 |

应用工程师的要点：**你调 API 用的都是走完三阶段的 Instruct 模型**。Base 模型给你续写，Instruct 模型给你答案。

### 4. 模型命名解读

以 `Qwen3.5-27B-Instruct-Q4_K_M` 为例，从左到右拆：

- **Qwen3.5**：模型系列 + 代次
- **27B**：参数量 270 亿（B = Billion）。参数越多通常越聪明，但显存和延迟也越高。8B 是入门线，27B~30B 是你这台机器（22G 显存）的甜点位，200B+ 一般只能云端
- **Instruct**：经过 SFT/RLHF 的对话版（对应的 `Base` 版只用于续写和二次训练）
- **Q4_K_M**：量化格式。原始权重是 FP16（每参数 2 字节），Q4 把权重压到约 4 bit（每参数约 0.5 字节），显存占用降到约 1/4，能力损失通常只有几个百分点

还有一种 2026 年很常见的写法：`Qwen3-30B-A3B`，`A3B` 表示 **MoE 架构下每次前向只激活约 3B 参数**。显存要按总参数（30B）算，速度按激活参数（3B）算——这就是为什么 30B 的 MoE 模型能比 14B 的稠密模型跑得还快。

显存粗算公式：**FP16 模型 ≈ 参数量 × 2 GB；Q4 ≈ 参数量 × 0.55 GB，再加 2~8GB 上下文开销**。
所以 27B-Q4 ≈ 15~17 GB，你的 22GB 显存跑起来还有余量给 KV cache；35B-Q4 ≈ 24 GB 就超了（详见 [[Ollama本地模型]]）。

其他常见后缀速查：

| 后缀 | 含义 |
|---|---|
| `-Chat` | 早期对话版命名，与 Instruct 同义 |
| `-Coder` | 代码特化微调版（如 qwen3-coder） |
| `-VL` | Vision-Language，能看图（见 [[多模态视觉API]]）。注意新一代主力模型常已原生多模态，不再单出 VL 版 |
| `-A3B` / `-A22B` | MoE 模型的激活参数量（如 30B-A3B = 30B 总参 / 3B 激活） |
| `AWQ` / `GPTQ` / `GGUF` | 不同量化方案/文件格式，GGUF 是 Ollama/llama.cpp 使用的格式 |
| `128K` / `256K` | 上下文窗口长度（见 [[Token与上下文窗口]]） |

### 5. 一次 API 调用在服务端发生了什么

理解这两个阶段，后面很多现象（计费、延迟）就有了解释框架：

```text
你的 messages
   ↓ 拼接成对话模板 + tokenize（见 [[Token与上下文窗口]]）
① prefill 阶段：整个输入一次性并行前向计算 → 输入越长，首字越慢
   ↓
② decode 阶段：逐 token 循环生成 → 每秒几十 token，决定"打字速度"
   ↓ detokenize
返回文本（流式则每个 token 立即推送，见 [[流式输出与SSE]]）
```

- 输入/输出分开计价的底层原因：prefill 与 decode 的算力成本结构不同
- 首字延迟（TTFT）≈ 排队 + prefill 时间，所以砍历史、精简 prompt 能直接降低延迟

### 6. 应用工程师常见误区

- **"模型在思考"**：它没有思考，只是在算下一个 token 的概率。拟人化理解会导致错误的调试直觉
- **"它说得这么肯定，应该是真的"**：置信的语气是训练出来的文风，与事实正确性无关
- **"多问几次取多数"是万能的**：对随机性错误有效，对系统性知识缺失无效（10 次都会编同一个不存在的 API）
- **"模型会学习我们的对话"**：API 调用不会改变模型权重，它下次照样不认识你；"记忆"要靠应用层自己实现
- **"参数越大越好"**：8B~14B 处理格式化任务（抽取/分类/改写）已足够，盲目上大模型只是浪费钱和延迟。云端同理——`deepseek-v4-flash` 比 `deepseek-v4-pro` 便宜 3 倍，简单任务上效果没差
