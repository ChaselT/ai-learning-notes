# 采样参数详解

## 这是什么/为什么重要

LLM 每一步是从概率分布里"采样"下一个 token（见 [[大语言模型工作原理速览]]），采样参数就是控制这个随机过程的旋钮。类比 JVM 调优参数：默认值能跑，但懂参数的人能让代码生成稳定可靠、让创意写作不千篇一律。参数用错是"输出忽好忽坏"的常见原因。

## 核心内容

### 1. temperature：随机性总开关

对概率分布做"锐化/钝化"：温度低 → 高概率 token 更容易被选中（趋向确定）；温度高 → 概率被拉平（更随机、更有多样性）。

**机制（面试常问，务必讲得出）**：模型每步为词表里每个 token 算出一个原始分数 **logits**，要过 **softmax** 才变成概率。temperature 干的事只有一件——**在 softmax 之前把所有 logits 除以 T**：

```
不带温度:  p_i = softmax(logit_i)
带温度:    p_i = softmax(logit_i / T)
```

| T | 数学效果 | 表现 |
|---|---|---|
| T < 1 | logits 差距被**放大** | 分布变尖，高分 token 近乎垄断 → 确定 |
| T = 1 | 原样 | 训练时的原生分布 |
| T > 1 | logits 差距被**压缩** | 分布被拉平，低分 token 也有机会 → 发散 |
| T → 0 | 差距无限放大 | 退化为贪心（argmax），永远选最大的 |

举例：候选 `"宝典"logit=4.0` 与 `"秘籍"logit=3.0`（差 1.0）。T=0.5 时变成 8.0 vs 6.0（差 2.0，"宝典"碾压）；T=2.0 时变成 2.0 vs 1.5（差 0.5，"秘籍"大有机会）。

⚠️ **关键区分**：temperature **不改变 token 的相对排序**，只改变"第二名有多大机会翻盘"——它无法让模型"想出"原本想不到的词。真正裁剪候选集合的是 `top_p`/`top_k`。**一个调概率、一个调候选范围**，这是两者的本质区别。

📌 **实测（2026-08 本机）**：`temperature=0` 并非 100% 确定——本地 qwen3.5:27b 连跑 10 次，第 1 次与后 9 次不同（9/10 一致）。原因不是模型在随机，而是**计算本身不完全可复现**：批处理顺序、浮点累加次序、MoE 专家路由都会带来微小数值差异，当两个候选概率极接近时足以翻盘。要尽量复现需同时设 `seed`（且 provider 支持）。

- `temperature=0`：近似贪心，每步选最大概率 token，输出最稳定
- `temperature=0.7`：多数对话场景的默认值附近
- `temperature=1.5+`：明显放飞，容易语无伦次

⚠️ **2026 年的新变化**：一批推理型模型（Claude 4.6 之后的 Opus/Sonnet 系列、部分 GPT-5.x 推理档）**已经彻底移除了 `temperature`/`top_p`/`top_k`**，传了直接返回 400，改用"思考力度"（effort/thinking）这类参数控制。

🚨 **比"报 400"更坑的第三种情况：静默忽略**（2026-08 本机实测）。经中转站调 gpt-5.6-sol 时，`temperature` 从 0 调到 1.4 **输出发散度毫无变化、甚至跑出逐字相同的结果**，且不报任何错；同一份代码只把 `base_url` 换成本地 Ollama，温度梯度立刻清晰可见。**结论：参数在中转层被丢弃了。**

**怎么判定参数有没有生效**（通用方法，比观察效果可靠）：
1. **传非法值探边界**——如 `temperature=99`。正常 provider 会返回 400（范围校验）；**不报错就说明根本没人处理这个参数**
2. **高低温对照 + 量化发散度**——同 prompt 各跑 5 次，把输出丢进 `set()` 数不同项；低温应接近 1、高温应接近 5。**单测低温证明不了任何事**
3. **prompt 必须选答案空间大的开放题**（起名字 ✅ / "1+1等于几" ❌）——候选只有一个时，温度无从发挥

📌 选型含义：**需要精确控制采样参数、或需要成本归因的场景，中转站不可靠**（它还会丢 `reasoning_tokens` 等扩展字段）。调参与评测请直连原厂或用本地模型。本篇讲的采样参数在 Chat Completions 生态（DeepSeek、通义、Ollama）里依然完全有效，但你在文档里看到"某模型不支持 temperature"时不要以为是 bug——那是模型有意去掉的。写通用封装时，把采样参数做成**可选透传**而不是必填。

```python
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],
                base_url="https://api.deepseek.com")

for t in (0.0, 0.7, 1.4):
    resp = client.chat.completions.create(
        model="deepseek-v4-flash",
        messages=[{"role": "user", "content": "给一款AI笔记应用起一个名字，只输出名字"}],
        temperature=t,
    )
    print(f"temperature={t}: {resp.choices[0].message.content}")
```

### 2. top_p：核采样（nucleus sampling）

只从"累计概率达到 p 的最小 token 集合"里采样，砍掉长尾。`top_p=0.9` 表示只在覆盖 90% 概率质量的候选里选。

**惯例：temperature 和 top_p 只调一个，另一个保持默认**（两个都动很难推断行为）。日常调 temperature 即可。

### 3. max_tokens：输出长度上限

限制**本次输出**最多生成多少 token（不含输入）。作用：

- 成本兜底：防止模型刹不住车生成几千 token
- 到达上限会**硬截断**，`finish_reason` 为 `"length"`（正常结束是 `"stop"`）——生产代码要检查这个字段，截断的 JSON 是不完整的

**`finish_reason` 四个取值与生产写法**：

| 值 | 含义 |
|---|---|
| `stop` | 模型自己结束（⚠️ 也可能是 refusal，见下） |
| `length` | 撞上 max_tokens 被硬截断 |
| `tool_calls` | 模型要调工具，`content` 为空、内容在 `message.tool_calls`（见 [[Function Calling]]） |
| `content_filter` | **平台安全层**拦截（多见于 Azure OpenAI） |

🔑 **易混点**：**模型自己拒绝 ≠ 平台拦截**。模型拒绝时走 `message.refusal` 字段，而 `finish_reason` **仍然是 `stop`**——只看 finish_reason 会误判为"一切正常"。

```python
match resp.choices[0].finish_reason:
    case "stop":
        if resp.choices[0].message.refusal:      # 模型主动拒绝
            logger.info("模型拒绝回答：%s", resp.choices[0].message.refusal)
        else:
            logger.info("正常完成")
    case "length":
        logger.warning("被截断，JSON 可能不完整")
    case "tool_calls":
        ...                                       # 走工具调用流程
    case "content_filter":
        logger.warning("被平台安全策略拦截")
    case _:                                       # 各家取值不一致，必须兜底
        logger.error("未知 finish_reason：%s", resp.choices[0].finish_reason)
```

⚠️ **最容易误解的一点**：`finish_reason == "stop"` 只说明**流程正常结束**，**与内容是否正确毫无关系**。实测用 0.5B 模型问 JVM 垃圾回收，`finish_reason` 是 `stop`，内容却几乎全是幻觉（编出"账本管理""家庭线""JGRT"等不存在的概念）。**检查 finish_reason 是必要条件，不是充分条件。**

```python
resp = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[{"role": "user", "content": "详细介绍Spring的历史"}],
    max_tokens=50,
)
print(resp.choices[0].finish_reason)  # "length" -> 被截断了
```

### 4. stop：停止序列

模型一旦生成指定字符串就立即停止（该字符串本身不出现在输出里）。适合限定格式：

```python
resp = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[{"role": "user", "content": "列出3种设计模式，每行一种，编号开头"}],
    stop=["4."],  # 生成到 "4." 就停，确保只出3条
)
```

### 5. frequency_penalty / presence_penalty

- `frequency_penalty`（-2~2）：按出现**次数**惩罚重复 token，正值减少复读机现象
- `presence_penalty`（-2~2）：只要**出现过**就惩罚，正值鼓励换新话题

默认 0。模型陷入重复循环（本地小模型偶发）时，调到 0.5~1.0 常能解决。

### 6. 场景推荐值

| 场景 | temperature | 其他 |
|---|---|---|
| 代码生成、SQL、正则 | 0 ~ 0.2 | 求稳定正确 |
| 结构化输出/信息抽取 | 0 | 配合 JSON mode，见 [[结构化输出]] |
| 客服/知识问答 | 0.3 ~ 0.7 | 平衡自然与靠谱 |
| 创意写作、头脑风暴 | 0.9 ~ 1.3 | 要多样性 |
| Function Calling 决策 | 0 ~ 0.3 | 工具选择要稳，见 [[Function Calling]] |

### 7. 可复现性问题

**`temperature=0` 也不保证逐字节可复现**：GPU 浮点运算的非确定性、服务端批处理、供应商悄悄更新模型，都会导致同一输入偶尔产出不同结果。部分 API 提供 `seed` 参数 + 响应里的 `system_fingerprint`，能提高（但不承诺）复现率。

工程结论：**不要写依赖 LLM 逐字输出相等的断言/测试**。测试 LLM 输出应该断言"结构与关键字段"（如 JSON 能解析、字段齐全），而不是全文相等。

```python
# 带 seed 的调用（OpenAI 官方端点支持，兼容端点看各家文档）
resp = client.chat.completions.create(
    model="gpt-5.6-luna",
    messages=[{"role": "user", "content": "随机举一个设计模式"}],
    temperature=0,
    seed=42,   # 尽力而为的复现，不是硬保证
)
print(resp.system_fingerprint)  # 后端配置指纹，指纹变了则结果可能不同
```

### 8. 调参 checklist

排查"输出不稳定/质量差"时按顺序检查：

1. 场景对号入座：确定性任务先把 `temperature` 归 0
2. 检查 `finish_reason`：是不是被 `max_tokens` 截断了
3. temperature 和 top_p 是否被同时改动（只留一个）
4. 输出重复复读 → 加 `frequency_penalty=0.5~1.0`
5. 参数没问题仍不稳 → 大概率是 prompt 问题，转 [[Prompt工程]] 的调试方法
